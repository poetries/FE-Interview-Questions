# 原型链

⚡ 30 秒速记

  • 对象通过内部 [[Prototype]] 连接成链，属性不存在时会沿链向上查找
  • 构造函数的 prototype 是实例原型，不等于构造函数自身的原型
  • 查到 null 结束；共享方法、继承与 instanceof 都建立在这条链上

原型链就是对象通过内部 [[Prototype]] 逐级连接起来的查找链，访问自身不存在的属性时会沿链向上寻找。 构造函数的 prototype 是实例使用的原型，并不等于构造函数自身的原型；链最终到达 Object.prototype，再向上就是 null。共享方法、继承和 instanceof 都依赖这套关系。实际排查属性来源时，可以逐级查看原型，避免把实例属性和继承属性混在一起。

  • 每个对象有 proto，指向构造函数的 prototype
  • 找属性沿着链向上找，到 Object.prototype 还没有就 undefined
  • Function.__proto__ === Function.prototype（鸡生蛋蛋生鸡）
  • Object.prototype.__proto__ === null（链尾）

简版：对象通过 proto 串成链，查属性沿链向上找，链尾是 null。

展开回答与验证思路

回答“原型链”时，先明确问题讨论的对象、输入和运行环境，再沿核心调用链或状态变化逐步解释。每一步都要说明由什么触发、读取了什么状态、产生什么结果，以及结果怎样交给下一步；这样才能把结论与正文依据对应起来，而不是只背一句定义。

完整回答还要补充适用条件、失败路径、替代方案和可验证证据，避免把单一结论说成普遍规则。 落到工程实践时，还要给出正常路径、失败路径和观测方法：用最小示例验证正确性，用日志、性能面板、网络面板或测试用例验证关键假设；存在多种实现时，说明当前方案在复杂度、性能、兼容性和维护成本上的取舍，以及条件变化后何时切换方案。

💬 面试官追问

  • 页面里执行 user.name 得到继承值，但 user 自身没有 name，同事断言属性不存在，你如何用代码现象反驳？

    自身没有属性不代表读取结果一定是 undefined，属性查找还会沿原型链向上进行。可分别检查对象自身和其原型上的 name，再删除或遮蔽原型属性观察结果；只有查到链尾 null 仍未命中时才返回 undefined。

  • 组件配置对象需要继承一组默认值，同时允许实例覆盖，你会怎样解释读取优先级和维护风险？

    读取时先查配置对象自身，未命中才沿原型链查默认对象，因此实例上的同名属性会遮蔽继承值。工程上应明确哪些字段允许继承，并避免随意修改共享原型；否则一个默认值变更可能影响多个实例，排查成本也会上升。

  • 安全模块传入一个原型链尾部就是 null 的字典对象，旧代码却假设所有对象最终都能访问 Object.prototype，哪里会失效？

    该字典不会继续连接到 Object.prototype，旧代码对链结构的假设因此不成立。应按实际原型逐级检查，并把 null 视为终点；若业务依赖通用对象能力，需要显式调用可靠方法或先转换结构，不能假定继承存在。

  • 线上出现 settings.theme 被意外改写，但日志显示 settings 自身从未赋值，你会怎样沿原型链定位？

    先确认 settings 是否拥有自有 theme，再逐级检查原型上的同名属性及最近的修改位置。还要区分“读取到继承值”和“自身已覆盖”两种状态；若共享原型被修改，影响范围可能跨越多个对象，修复时需同时审计创建关系。

  • 面试中有人把 Function.__proto__ === Function.prototype 当成所有原型关系的通用模板，你会用哪个链尾事实纠正？

    该等式是特定对象关系，不能据此推导所有对象的原型都指向自身或形成无限循环。沿链查找最终仍以 Object.prototype.__proto__ === null 收束；分析时应逐个确认对象及其原型，而不是套用单个特殊关系。
