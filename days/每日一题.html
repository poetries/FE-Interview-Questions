# 第386题 面向对象的三大特性

⚡ 30 秒速记

  • 封装：把状态收进对象内部只暴露方法，JS 里靠闭包、WeakMap 或 # 私有字段实现，下划线前缀只是约定
  • 继承：把公共能力放在原型上共享，class extends 的本质是把子类原型接到父类原型上
  • 多态：同一个调用点因实例不同走不同实现，JS 不需要额外语法，属性查找沿原型链先找到谁就用谁
  • 三条在 JS 里全部落在原型链上，讲清「原型链怎么查找」比背定义值钱
  • 加分点：JS 没有真正的类，class 只是构造函数的语法糖，主动点破这句能显出理解深度

面向对象的三大特性是封装、继承和多态，在 JavaScript 中理解它们离不开原型链。 封装是把状态收在对象内部，只暴露必要方法，可通过闭包、WeakMap 或 # 私有字段实现。继承本质上是复用原型上的公共能力，class extends 会把子类原型连接到父类原型；多态则是同一调用因实例不同而执行不同实现。实际判断时，我会结合对象创建方式、instanceof 和 new 的原理，看属性最终沿原型链查到了哪里。

  • 封装
  • 继承
  • 多态

原型链的知识

原型链是面向对象的基础，是非常重要的部分。有以下几种知识：

  • 创建对象有几种方法
  • 原型、构造函数、实例、原型链
  • instanceof的原理
  • new 运算符

💬 面试官追问

  • 订单对象把 status 和 amount 都公开给页面组件，任何组件都能绕过校验直接赋值；团队却说用了 class 就算完成封装，你会怎么评价？

    使用 class不等于完成封装，公开状态仍可能被任意调用方破坏。应隐藏可变数据，并通过职责明确的方法维护状态约束，让对象自己保证合法性；代价是调用路径更严格，接口设计不当也会形成过度封装。

  • 支付模块有 CardPayment 和 WalletPayment 两种实现，业务层到处写 if 判断具体类型；新增第三种支付方式时要改十几个页面，如何用多态收敛？

    应让不同支付实现暴露统一操作，由业务层面向共同约定调用，而不是分支识别具体类型。新增实现时主要扩展新对象，调用方无需了解内部差异；若各支付方式的输入和失败语义差异过大，强行统一接口会掩盖真实约束。

  • 组件库准备让 DangerButton 继承 Button，但它需要删除父类允许的某些交互，并改变点击语义；你会继续用继承吗？

    不宜只为复用样式就建立继承关系，因为子类若不能保持父类的行为约定，会让调用方产生错误预期。可把视觉和公共能力拆成组合模块，再由不同组件组装；组合会增加一些连接代码，但能避免脆弱的层级关系。

  • 线上发现 instanceof 判断始终为 false，对象的方法却能正常调用；排查时你会从原型链的哪个方向入手？

    instanceof判断的是构造函数的 prototype 是否出现在对象的原型链上，不是检查对象长得是否相同。应核对对象的创建方式、构造函数引用以及原型是否被整体替换；来自不同执行环境的同名构造函数也可能使该判断失效。

  • 旧代码用构造函数创建对象，新成员漏写 new 后把属性写到了错误上下文；请你说明 new 在这段创建流程里承担了什么？

    new会创建对象，并把新对象连接到构造函数的 prototype，再以该对象作为调用上下文执行构造函数。构造函数若显式返回对象，最终结果还可能被替换；因此不能只把 new理解成一次普通函数调用。

  • 一个数据模型只需要复用少量行为，评审却计划建立五层继承树；从封装、继承和多态的关系看，你会怎样取舍？

    三种特性不是必须同时堆叠，封装负责守住状态边界，多态负责让调用方依赖统一行为，继承只是复用和建立类型关系的一种手段。层级过深会放大父类变更影响；关系不稳定或只是能力复用时，组合通常更容易控制边界。
